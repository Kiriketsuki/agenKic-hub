    Feature: Hub Plugin Marketplace¶

    Overview¶

    User Story: As a user of the hub, I want one install command and marketplace updates. Hooks and workflows then wire themselves, and CI proves the package loads.

    Problem: The hub ships through a symlink installer. Hooks need a hand merge into settings.json, and Windows needs a junction fallback. Every update means a re-run. Nothing validates the package, and no eval checks that a skill triggers or helps.

    Out of Scope: The repo restructure itself. This PR delivers the spec only. Anthropic directory submission. claude.ai and Cowork support. Hooks for Codex, OpenCode, Pi or Hermes. A rewrite of any skill body beyond its references and configuration lines.

    Success Condition¶

    This feature is complete when a user adds the marketplace with claude plugin marketplace add Kiriketsuki/agenKic-hub and installs the four plugins. Every skill, workflow and hook must then work under its namespaced name with no settings.json edit. CI must also pass claude plugin validate --strict and the core eval suite.

    Scope¶

    Must-Have¶

    • Marketplace and four plugins: .claude-plugin/marketplace.json at the repo root lists agenkic-core, agenkic-council, agenkic-writing and agenkic-ops. Acceptance: claude plugin validate . --strict exits 0.
    • Namespaced references: every cross-skill reference names the namespaced skill and keeps the bare name for other harnesses. Acceptance: the inventory in section 2 has no open row.
    • Plugin hooks: hooks/hooks.json in agenkic-ops and agenkic-core replaces the settings.hooks.example.json merge. Acceptance: a migrated machine runs each hook once per event.
    • Plugin workflows: orchestration workflows ship as .js files in agenkic-council. They run as /agenkic-council:<name>. Acceptance: /agenkic-council:spec-loop starts, and its nested council-loop call resolves.
    • userConfig: the skill settings in section 5 move to userConfig, with an environment fallback. Acceptance: feature-spec reads vault_path from the configure dialog.
    • Smaller installer: the installer keeps config/, the external components and the links for non-Claude harnesses. Acceptance: no installer step writes into ~/.claude/hooks/ or ~/.claude/workflows/.
    • CI: one job runs claude plugin validate --strict. A second job runs claude plugin eval on four core skills. Acceptance: both jobs gate PRs.
    • Migration path: setup/migrate-to-plugins.sh removes the legacy hook entries and links. Acceptance: a dry run lists every change, and a backup restores the old state.

    Should-Have¶

    • A SessionStart warning in preflight-check.sh when settings.json still wires a hub hook.
    • An agenkic-ops toggle that turns the continuous-learning-v2 observer on.

    Nice-to-Have¶

    • An agenkic-all bundle plugin.
    • Evals for one council skill and one writing skill.

    Technical Plan¶

    1. Plugin split and directory layout¶

    Decision: each skill group directory becomes a plugin root in place. The marketplace root is the repo root.

    Evidence for the layout:

    • A plugin is a directory with .claude-plugin/plugin.json. Only the manifest goes inside .claude-plugin/ [docs: plugins/create#plugin-layout].
    • The skills key adds directories to scan, and "." or "./" names the plugin root [docs: plugins/manifest-reference#path-only-fields].
    • A marketplace entry source is a relative path from the marketplace root [docs: plugins/create-marketplace#write-relative-paths-from-the-marketplace-root].
    • A group root with "skills": ["./"] loaded its skill directories. The hooks/ and workflows/ subdirectories did not load as skills, because they hold no SKILL.md [probe].
    • A copied plugin loses every file outside its own directory [docs: plugins/loading#in-place-and-copied-plugins]. No skill links into another group today. Section 2 lists the ../ links, and all stay inside one group [repo].

    2. Namespacing and cross-skill references¶

    Rules from the docs:

    • A plugin skill runs as /<plugin>:<name>. The frontmatter name sets the last segment [docs: skills#how-a-skill-gets-its-command-name].
    • The docs say a bare /<name> also invokes a plugin skill that sets name, unless another command owns it [docs: skills#how-a-skill-gets-its-command-name]. A claude -p probe of a bare /hello did not run the plugin skill [probe]. The spec therefore uses the namespaced form everywhere.
    • A command file in a subdirectory gains a segment, so commands/db/migrate.md is /my-plugin:db:migrate [docs: plugins/components#commands].
    • A manifest commands directory path names the commands after each file. The exact segment form for a listed directory is [unverified].
    • All 26 skills set a frontmatter name today [repo].

    Reference style for Claude Code and other harnesses:

    Use the agenkic-core:context-handoff skill (/context-handoff in a linked install).

    Codex and OpenCode read the same SKILL.md through links, so the bare name stays in parentheses.

    3. Hooks¶

    Decision: the hub hooks ship in plugin hooks/hooks.json files. Each command reads its script through ${CLAUDE_PLUGIN_ROOT}.

    Evidence:

    • hooks/hooks.json holds a top-level "hooks" key in the same shape as the hooks object in settings.json, so the hub entries copy in unchanged [docs: plugins/components#hooks].
    • A shell-form command wraps ${CLAUDE_PLUGIN_ROOT} in double quotes [docs: plugins/components#environment-quoting-and-matching-mcp-tools].
    • Each hook process receives CLAUDE_PLUGIN_ROOT, CLAUDE_PLUGIN_DATA and one CLAUDE_PLUGIN_OPTION_<KEY> per option [docs: plugins/manifest-reference#where-each-variable-resolves].
    • Plugin hooks register at load and fire on every matching event. They do not wait for a skill to run [docs: plugins/components#when-plugin-hooks-fire].
    • A hook in both settings.json and hooks/hooks.json runs twice per event [docs: plugins/create#convert-an-existing-claude-setup].
    • A plugin settings.json honors only agent and subagentStatusLine [docs: plugins/components#default-settings]. The permissions.ask rule for Bash(gh pr merge *) therefore stays a manual settings entry.
    • A [probe] loaded a SessionStart hook from hooks/hooks.json with a quoted ${CLAUDE_PLUGIN_ROOT} path.

    Placement:

    Hook script Event Plugin Toggle (userConfig, boolean) Default
    gh-check-before-create.sh PreToolUse Bash agenkic-ops enforce_naming true
    pre-push-auth.sh PreToolUse Bash, if: Bash(git push *) agenkic-ops pre_push_auth false. It switches the active gh account, which surprises a new user
    lint-precommit.sh PreToolUse Bash, if: Bash(git commit *) agenkic-ops lint_precommit true
    large-file-check.sh PreToolUse Bash, if: Bash(git commit *) agenkic-ops large_file_check true
    preflight-check.sh SessionStart agenkic-ops None Always on. It only warns
    python-syntax-check.sh PostToolUse Edit, Write agenkic-ops None Always on. It only reports
    context7-suggest.sh PostToolUse Read agenkic-ops None Always on. It only nudges
    stop-verify-gate.sh Stop agenkic-ops stop_verify_gate true
    continuous-learning-v2/hooks/observe.sh PreToolUse and PostToolUse, matcher * agenkic-ops observe_sessions false. It fires on every tool call
    agent-route-suggest.sh PreToolUse Agent, TeamCreate agenkic-core None Always on. It only nudges

    Migration without double runs. Order matters. No session runs between the removal and the plugin install.

    1. Run setup/migrate-to-plugins.sh --dry-run. It lists each hub entry in ~/.claude/settings.json. It matches a hook command that ends in hooks/<name>.sh for the nine known names, in any directory. That match covers the symlink install and the copy steps in docs/patterns/hooks.md.
    2. Run the script without --dry-run. It writes a backup with the installer's .bak naming. It removes the matched entries with jq. It removes each ~/.claude/hooks/<name>.sh link that points into the repo. It keeps the permissions block.
    3. Run claude plugin install agenkic-ops@agenkic-hub and claude plugin install agenkic-core@agenkic-hub.
    4. Start a new session. Run /hooks or claude --debug to confirm one entry per event.

    preflight-check.sh also warns at session start when settings.json still names one of the nine scripts. The plugin itself then reports a double wiring.

    Rollback: claude plugin disable agenkic-ops@agenkic-hub, then copy the settings.json backup back. For one release, harnesses/claude-code/hooks stays as a symlink to ../../skills/ops/hooks/scripts. Old links into it keep resolving. That symlink sits outside every plugin root, so the plugin cache never sees it.

    4. Workflows¶

    Decision: the orchestration workflows move to skills/council/workflows/ as .js files. Nested calls use the namespaced workflow name.

    Evidence:

    • Plugin workflows are .js files in workflows/ at the plugin root [docs: plugins/manifest-reference#standard-layout].
    • Plugin workflows run as /<plugin>:<meta.name> [docs: workflows#distribute-a-workflow-in-a-plugin].
    • A plugin demo.js ran as /agenkic-core:demo. A plugin demo2.mjs did not resolve [probe]. This matches the repo note that the name registry skips ~/.claude/workflows/*.mjs [repo: workflows/feature-loop.mjs:21-23].
    • claude plugin validate --strict passed a plugin with a .mjs workflow [probe]. Validation alone does not catch the extension.
    • workflow() takes a registry name or { scriptPath }. Nesting is one level deep. Scripts get no filesystem or Node.js API (bundled /workflow-authoring reference).
    • Inside a plugin workflow, workflow('agenkic-council:leaf', args) ran a workflow from a second plugin and passed args. A bare workflow('leaf') failed, and the error listed only namespaced names [probe].
    • ${CLAUDE_PLUGIN_ROOT} stayed literal inside a workflow script. The docs list no substitution for workflows [probe], [docs: plugins/manifest-reference#where-each-variable-resolves].
    • typeof process was 'undefined' inside the script [probe]. The current WF_DIR default therefore resolves to /.claude/workflows when the caller omits workflowsDir [repo: workflows/spec-loop.mjs:464]. That is a live bug.

    5. userConfig and template variables¶

    No skill uses a {{variable}} template today. Only config/tmux/tmux.conf.tmpl and config/zsh/agentic-hub.zsh.tmpl do [repo]. The skills take settings as environment-style names in a "Configuration" section instead. userConfig replaces those names. The {{variable}} templates stay with the installer.

    Evidence:

    • userConfig options appear in the /plugin install dialog and in /plugin configure. claude plugin install in a shell never prompts, but takes --config KEY=VALUE [docs: plugins/components#when-the-configuration-dialog-appears].
    • ${user_config.KEY} resolves in skill content for non-sensitive values only [docs: plugins/manifest-reference#reference-a-saved-value].
    • Types are string, number, boolean, directory and file. An unknown key inside an option fails validation [docs: plugins/manifest-reference#user-configuration].
    • An unset ${user_config.vault_path} stayed literal in the skill text [probe]. The result for "default": "" is [unverified].

    Variables that move to userConfig:

    Today Skill Plugin userConfig key Type
    $VAULT_PATH feature-spec agenkic-core vault_path directory
    $DAILY_NOTE_PATH feature-spec agenkic-core daily_note_path string
    $LETTERS_DIR cover-letter agenkic-writing letters_dir directory
    $VOICE_TEMPLATE cover-letter agenkic-writing voice_template file
    $FACTS_FILE cover-letter agenkic-writing facts_file file
    $INSIGHTS_ARCHIVE_DIR insights-to-vault agenkic-ops insights_archive_dir directory
    config.json observer.enabled continuous-learning-v2 agenkic-ops observe_sessions boolean
    None The hooks in section 3 agenkic-ops Five hook toggles boolean

    Each skill keeps an environment fallback, because Codex and OpenCode never substitute ${user_config.*}. The text pattern:

    Vault root: ${user_config.vault_path}. If that value is empty, or still reads ${user_config.vault_path}, use $VAULT_PATH. If both are unset, skip Step 5.

    continuous-learning-v2 edits config.json inside its skill directory today. The plugin root changes on every update, so an edit there does not carry over to the next version [docs: plugins/manifest-reference#environment-variables]. The observer reads ${CLAUDE_PLUGIN_DATA}/config.json first and seeds it from the shipped file.

    The installer keeps every job that a plugin cannot do.

    Component After the change

    ext-statusline, ext-tmux-theme, ext-dots Unchanged
    harness-codex, harness-opencode, harness-pi, harness-hermes Unchanged. Each gains a skills_dir= key once open question 10 settles
    skills-core, skills-council, skills-writing, skills-ops Link skills into the skills directory of each selected non-Claude harness. A new filter=SKILL.md key links only children that hold a SKILL.md. Without it, hooks/, workflows/, evals/, bin/ and commands/ leak into the targets
    workflows Removed in step M5. The plugin ships the workflows
    harness-claude-code Stops copying hooks into ~/.claude/hooks/. It prints the permissions.ask snippet to merge by hand

    New setup/migrate-to-plugins.sh The legacy cleanup in section 3, plus removal of hub skill and workflow links from ~/.claude/

    The bash glob in link_children skips dot entries, so .claude-plugin/ never links [repo: setup/setup.sh:379]. setup.ps1 calls Get-ChildItem without a dot filter [repo: setup/setup.ps1:153]. The filter=SKILL.md key fixes both.

    Codex and OpenCode keep the link install. A skill body that names ${CLAUDE_PLUGIN_ROOT}, ${CLAUDE_SKILL_DIR} or ${user_config.*} reaches them as literal text. Each such line therefore keeps a harness-neutral fallback, such as a path relative to the SKILL.md or an environment variable.

    Windows: plugins copy into the plugin cache, so Claude Code users no longer need the junction fallback [docs: plugins/loading#find-plugins-on-disk]. The Codex and OpenCode links on Windows still need it.

    The author's own machine links ~/.claude/skills to the vault Skills directory, and the vault links each hub skill [repo: setup/relink.sh:12-13]. After the plugin install, every hub skill loads twice, once bare and once namespaced [docs: plugins/create#convert-an-existing-claude-setup]. Set each hub skill to "off" in skillOverrides in ~/.claude/settings.json. skillOverrides does not touch plugin skills [docs: skills#override-skill-visibility-from-settings]. Codex keeps reading the vault links.

    7. CI¶

    Two new jobs in .github/workflows/plugins.yml.

    Job plugin-validate, on every PR:

    npm install -g @anthropic-ai/claude-code@2.1.303
claude plugin validate . --strict
for p in skills/core skills/council skills/writing skills/ops; do
  claude plugin validate "$p" --strict
done
test -z "$(find skills -path '*/workflows/*.mjs')"
    • Given the marketplace root, validate checks the marketplace and the plugin.json of each relative-path plugin [docs: plugins/create-marketplace#problems-that-validation-reports].
    • Given one plugin root, it checks the manifest and the frontmatter of every skill, agent and command [docs: plugins/create#test-and-debug].
    • --strict turns warnings into failures [docs: plugins/cli-reference#plugin-validate].
    • The find line fails on a .mjs workflow, which validate lets pass [probe].
    • Whether claude plugin validate runs without credentials is [unverified]. Step M1 confirms it on the first CI run.

    The existing ci.yml workflow job keeps its body-wrap syntax check. Its glob moves to skills/council/workflows/*.js in step M3.

    Job plugin-eval, on PRs that touch skills/core/** and on manual dispatch:

    claude plugin eval skills/core \
  --trust-plugin \
  --json results.json \
  --threshold 0.66 \
  --model claude-sonnet-5 \
  --no-publish \
  --max-cost-usd 5
    • Each case runs three times with the plugin and three times without it [docs: plugin-evals#how-a-case-is-scored].
    • --trust-plugin keeps CI off the trust prompt, and --json with a non-zero exit gates the job [docs: plugin-evals#run-evals-in-ci].
    • A threshold of 0.66 lets one of three runs miss.
    • A tool_used grader on Skill is a "plugin-fired indicator" in a two-arm run. It still counts when it is the only grader in a case [docs: plugin-evals#compare-against-a-no-plugin-baseline].
    • A no-trigger grader sets min: 0, max: 0 and arm: both, so the baseline arm scores it too [docs: plugin-evals#compare-against-a-no-plugin-baseline].
    • All graders are regex or tool_used, so no judge call adds cost [docs: plugin-evals#grade-the-result].

    Skills under eval: brainstorm, feature-spec, context-handoff and agent-route. Claude invokes each one on its own. implement-spec and merge-next set disable-model-invocation: true, so a trigger eval says nothing about them [repo]. The four chosen skills have neighbors that compete for the same phrasing: brainstorm-grill, brainstorm and model-route.

    Eight cases, one trigger case and one no-trigger case per skill:
