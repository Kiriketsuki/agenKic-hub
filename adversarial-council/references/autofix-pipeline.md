# Autofix Pipeline

Invoked when the user responds `y` to a CODE motion gate. Executes autonomously through 5 phases and pauses only at the merge decision.

---

## Phase 1 — Validate Findings

Read the recommendation file written by the ARBITER.

For each finding in the Suggested Fixes section:
1. Read the cited `file:line`
2. Confirm the issue exists exactly as described
3. Classify: **CONFIRMED** or **PHANTOM**

Phantom rules:
- Finding the QUESTIONER marked "unsubstantiated" → PHANTOM automatically
- Cited `file:line` does not contain the described issue → PHANTOM
- Finding is vague with no actionable code location → PHANTOM

Output:
```
[VALIDATE] Finding 1: CONFIRMED — cache.ts:142 null dereference confirmed
[VALIDATE] Finding 2: PHANTOM — auth.ts:88 does not contain the described pattern
[VALIDATE] Finding 3: CONFIRMED — utils/parse.ts:31 type coercion confirmed
[VALIDATE] Summary: 2/3 confirmed. 1 phantom removed.
```

Do not proceed to Phase 2 until all findings are classified.

---

## Phase 2 — Fix Team

Spawn agents in parallel:
- `FIXER-1` through `FIXER-N` — one per CONFIRMED finding (model: sonnet)
  - Each FIXER receives: the finding description, cited file:line, and the recommendation file path
  - Each FIXER: reads the file, applies the minimal fix, reports back the diff
- `REVIEWER` (model: sonnet)
  - Receives all diffs from FIXER agents
  - Checks: correctness, no regressions introduced, fix scope matches the finding
  - Reports: APPROVED or REJECTED (with reason) per fix

If REVIEWER rejects a fix, spawn `FIXER-N-v2` with the rejection reason and retry once. If still rejected, flag for human review and skip that fix.

---

## Phase 3 — Test

After all fixes are applied:

1. Detect test suite: check for `package.json` scripts (`test`, `test:unit`), `pytest`, `go test`, `cargo test`, `Makefile` with `test` target
2. If test suite found: run it
3. Capture output

```
[TEST] Suite detected: npm test
[TEST] Result: PASS (47 tests, 0 failures)
```

or:

```
[TEST] No test suite detected — skipping
```

If tests FAIL: report failures, but do NOT abandon the PR. The PR will note the failures.

Additionally, when tests FAIL, run a regression attribution pass:
1. For each failing test, identify which file(s) the failure implicates
2. Cross-reference with the fixes applied in Phase 2 (each FIXER reported its diff)
3. If a failing test overlaps with an area that a FIXER touched, mark it as a
   **potential regression** from that fix
4. Build a `REGRESSION_CANDIDATES` list:
   ```
   [REGRESSION] fix-N touched `src/auth/handler.py:142` -- failing test `test_login_flow`
                implicates `src/auth/handler.py` -- CANDIDATE
   ```
   Be conservative: only flag when the file overlap is direct. Do not speculate.

This list is used in Phase 4 (PR body) and Phase 6 (registry update).

---

## Phase 4 — PR

Create the pull request using `gh pr create`.

**Title format**: `fix: [motion-slug] — [N] findings addressed`

**Body format**:

```markdown
## Council Recommendation Summary

Motion: [motion text]
Arbiter verdict: [FOR / CONDITIONAL]
Council date: [YYYY-MM-DD]

## Validated Findings

| # | Finding | Status | Fix |
|---|---------|--------|-----|
| 1 | [description] | CONFIRMED | Applied |
| 2 | [description] | PHANTOM | Removed |
| 3 | [description] | CONFIRMED | Applied |

Phantoms removed: [K] (unsubstantiated or file:line mismatch)

## Test Results

[PASS (N tests) / FAIL (N failures — see details) / SKIPPED (no suite)]

[If REGRESSION_CANDIDATES is non-empty:]
## Potential Regressions Introduced
> The following fixes overlapped with test failures. These may be regressions.
> They will be logged to `council-fix-registry.md` for future councils to track.

| Fix | Location | Failing Test | Overlap |
|-----|----------|--------------|---------|
| [fix-N description] | [file:line] | [test_name] | [file] |

## Changes

[One line per fix: what was changed and why]

---
*Generated by adversarial-council autofix pipeline*
*Full council recommendation: [recommendation filename]*
```

Do NOT auto-merge. Leave PR open for human review.

---

## Phase 5 — Merge Gate (ONLY pause point)

Present this block to the user and wait:

```
────────────────────────────────────────
PR created: [URL]

Findings : [N confirmed] / [M total] ([K phantoms removed])
Tests    : [PASS / FAIL / SKIPPED]
PR       : [title]

Merge? [y/N]
────────────────────────────────────────
```

**`y`** → squash merge: `gh pr merge --squash --auto [PR-number]`
**`N`** (or no response / anything else) → leave PR open, inform user: "PR left open at [URL]. Merge when ready."

---

## Phase 6 — Fix Registry Update

Run this phase regardless of whether the user merged (`y`) or left the PR open (`N`).
The registry captures what this council fixed and what regressions it may have introduced,
so future councils can trace bug lineage.

**File:** `council-fix-registry.md` in the current working directory.

**Registry format** (append to the table, or create the file if it does not exist):

```markdown
# Council Fix Registry

| Council File | Motion | Fix Description | Fix Location | Regression Symptom | Regression Location | Resolved By |
|---|---|---|---|---|---|---|
| [council-md-filename] | [motion text] | [fix description] | [file:line] | [symptom or --] | [file:line or --] | -- |
```

**Filling in each row:**

- **Council File**: the recommendation `.md` filename (e.g. `2026-03-19-143022-council-fix-auth-bug.md`)
- **Motion**: the motion text (truncated to 60 chars)
- **Fix Description**: one-line description of what the fix did (from FIXER diff)
- **Fix Location**: `file:line` where the fix was applied
- **Regression Symptom**: if this fix appeared in `REGRESSION_CANDIDATES`, write the failing test name and a one-line symptom description. Otherwise: `--`
- **Regression Location**: the file implicated by the failing test. Otherwise: `--`
- **Resolved By**: always `--` at creation time. A future council will fill this in when it closes the regression.

**Closing prior regressions:**

After appending new rows, scan the existing registry for rows where `Resolved By = --`.
If the current council's motion explicitly addressed a prior regression (the recommendation's
"Prior Regressions Resolved" sub-section listed it), update that row:
- Set `Resolved By` to the current council file name

**Amend recommendation file:**

Back-fill the "Regressions Introduced by This Council's Fixes" sub-section in the
recommendation file with the entries just logged to the registry.

---

## Error Handling

| Situation | Action |
|---|---|
| Recommendation file not found | Abort. Inform: "Recommendation file not found. Rerun council to regenerate." |
| All findings are PHANTOM | Skip Phase 2–4. Inform: "All findings were unsubstantiated. No fixes applied." |
| FIXER agent fails twice | Skip that finding. Note it as "fix attempted but failed" in PR body. |
| `gh` not authenticated | Abort Phase 4. Inform: "gh CLI not authenticated. Run `gh auth login` then retry." |
| PR creation fails | Inform user with exact error. Leave diffs in working tree. |

---

## Fallback

If this file (`references/autofix-pipeline.md`) does not exist when the `y` response is processed, fall back to the previous behavior: enter plan mode and present the full implementation plan for user approval.
